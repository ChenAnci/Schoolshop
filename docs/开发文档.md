## 1. 项目概述

构建一个前后端分离的**校园二手/闲置/商品交易市场系统**，覆盖三类角色：管理员（后台运营）、商家（发布与售卖商品）、用户（浏览、下单购买）。交易模式为**线上生成订单 + 线下自提 / 当面交易**，系统仅管理订单流转状态，不在本期接入真实在线支付。

### 1.1 已确认的技术决策

| 项 | 决策 |
| --- | --- |
| 后端 | SpringBoot **4.1.x** + **Java 17**（基于 RuoYi 3.9.2 基线，本机已装 JDK17 完全匹配） |
| ORM | RuoYi 自带 MyBatis + PageHelper；MyBatis-Plus 是否作为业务模块 ORM 引入 `[待确认]` |
| 数据库 | MySQL 8 |
| 缓存 | Redis |
| 鉴权 | **长短双 Token**（JWT access token 短时 + refresh token 长时长驻 Redis） |
| 后端骨架 | 基于 **RuoYi 3.9.2**（SpringBoot 4.1 后端，多模块已落地于根目录）扩展 |
| 前端 | Vue3 + Element Plus + Vite + Pinia，**三端各自独立前端项目**（均基于 RuoYi-Vue3 前端模板衍生） |
| 用户端形态 | Vue3 **Web 电脑端**（PC 电商风格 SPA） |
| AI 模块 | 独立 Python 服务（LangChain + LangGraph），本期**预留对接接口与骨架**，后续为管理端提供数据分析 |
| 交易模式 | 线上订单 + 线下自提 / 当面交易，**不接真实支付** |

```

        ┌────────────────┼────────────────┐
        │                │                │
  campus-admin      campus-merchant   campus-user
    管理端(基于RuoYi-Vue3) 商家端(Vue3)    用户端(Vue3)
        └────────────────┼────────────────┘
                         ▼
               Nginx (静态资源 + 反代 + CORS)
                         ▼
 ┌────────────────────────────────────────────────┐
 │            SpringBoot 后端 (RuoYi-Vue3 扩展)      │
 │  Auth模块 | 商品模块 | 订单模块 | 商家/店铺模块      │
 │  用户/角色权限 | 文件上传 | 数据分析代理(调AI)       │
 │  长短双Token(Redis) | MyBatis-Plus | MySQL       │
 └──────┬──────────────────────────┬───────────────┘
        │                          │
     MySQL                                      │
   (业务+权限+审计)            HTTP(REST) / 定时任务
        │                          ▼
   Redis                 Python AI 服务(预留)
   (token/会话/缓存)        LangChain + LangGraph
                            管理端数据分析(预留)
```

- **统一后端**：三端复用同一 SpringBoot 服务，通过角色(admin/merchant/user)与权限控制访问范围。

- **AI 服务**：独立 Python 进程 + 独立端口，后端通过 HTTP 代理调用；本期只定契约和骨架。

## 6. 鉴权设计：长短双 Token

在 RuoYi 的 JWT + Redis 基础上，改为**长短双 Token**：

### 6.1 流程
```
登录 → 校验账号密码 → 签发 accessToken(短) + refreshToken(长, 存Redis)
所有业务接口 → 校验 accessToken → 有效则放行
accessToken 过期(401) → 前端带 refreshToken 调 /auth/refresh
  → 校验 refreshToken 与 Redis 一致 → 签发新 accessToken(可选轮换 refreshToken)
退出登录 → 删除 Redis 中 refreshToken → accessToken 加入黑名单直至过期
```

- **accessToken**：JWT，有效期短（如 30 分钟），包含 `userId`、角色；无状态校验。
- **refreshToken**：有效期长（如 7 天），签发时写入 Redis（key：`refresh:<userId>`），用于刷新 access，且可被服务端主动作废（封禁账号即清除）。
- 接口鉴权复用 RuoYi 的 Spring Security + JWT 过滤器，控制器用 `@PreAuthorize` 控制角色与权限点。

### 6.2 前端配合
- axios 拦截器：请求头带 `Authorization`；收到 401 时自动用 refreshToken 刷新并重放原请求（并发场景对刷新做单飞去重）；refresh 也失败则跳登录页。

### 6.3 统一登录入口 + 按角色跳转 + 权限隔离（已实现 ✅）
系统**不分端各自登录**，仅用户端 8083 提供唯一登录入口，登录后按账号角色自动跳转到对应端。

```
8083 统一登录(/login) → 校验 → 调 /getInfo 拿角色 →
  含 admin 角色    → 跳 http://localhost:8081/?token=<accessToken>
  含 merchant 角色 → 跳 http://localhost:8082/?token=<accessToken>
  否则(用户)      → 留在 8083 用户端
```

- **跨端 token 传递**：各端运行在不同源（8081/8082/8083），localStorage 不互通，故登录成功后通过 URL `?token=` 携带 short JWT 跳转；目标端路由守卫读取 URL token 存入本地并 `replace` 清除 URL 参数，防止 token 泄露在地址栏。
- **前端权限隔离**：三端路由守卫均为首次进入校验：
  - 管理端 8081 守卫：仅放行含 `admin` 角色，未登录/非管理员一律 `window.location.href` 回 `//localhost:8083/login`。
  - 商家端 8082 守卫：仅放行含 `merchant` 角色，否则回统一入口。
  - 用户端 8083 守卫：游客可浏览公开页，需登录页经 `requiresAuth` 拦截。
- **后端权限隔离**：
  - 业务写接口沿用 RuoYi `@PreAuthorize("@ss.hasPermi('market:xxx')")` 按权限点控制。
  - 商家专属作用域接口（如 `/market/shop/my`）额外加 `@PreAuthorize("@ss.hasRole('merchant')")`，保证只能商家调用。
  - 游客公开浏览接口 `/market/browse/**` 在 `SecurityConfig` 放行（permitAll），游客可不登录浏览店铺/商品。
- **登录页/路由守卫对接细节**：
  - `/getInfo` 返回 `{ user, roles, permissions }`（角色在**顶层**，非 `data` 内），`getInfo()` 返回类型为 `UserInfo`，store 直接读 `roles`.
  - 验证码：仅当后端 `captchaEnabled=true` 时必填；图片 `data:image/jpeg;base64`。

## 7. 订单状态机（线下自提/当面交易）

```
用户下单(待商家接单) ──▶ 商家接单(待自提) ──▶ 用户确认提货/mark完成 ──▶ 已完成
   │                        │
   │(用户取消/超时)          │(商家取消)
   └──▶ 已取消 ◀────────────┘
   │
   ▷ 异常单(用户投诉/争议) → 管理员审查(audit_flag) → 仲裁：恢复流转 或 强制已完成/取消
```

| 状态码 | 状态 | 说明 |
| --- | --- | --- |
| 0 | 待商家接单 | 用户下单后等待商家确认 |
| 1 | 待自提/待提货 | 商家已接单，通知用户线下自提或当面交易 |
| 2 | 已完成 | 用户确认货品交付 |
| 3 | 已取消 | 用户/商家取消（记录 reason） |
| 4 | 审查中 | 争议/投诉订单，管理员介入（仅管理员可操作） |
| 5 | 审查完成(仲裁) | 管理员给出处理结论并入审计日志 |

> 状态流转由后端校验合法性，子项表 `order_item` 随主订单状态联动。订单号生成规则与并发唯一性以 `redis + 序号` 或时间戳+随机数实现。

## 8. 功能模块与权限

### 8.1 管理端（campus-admin）
- 登录/退出/修改密码（双 Token）

### 8.3 用户端（campus-user）

## 9. AI 模块设计（LangChain + LangGraph，预留）

### 9.1 定位
给**管理端**做数据分析（如销售趋势、热销/滞销商品、商家维度统计、异常订单识别等），本期**预留接口占位**，不影响核心系统。

### 9.2 对接契约（本期先冻结）
- AI 服务独立端口，暴露：
  - `GET /health` 健康检查
  - `POST /analysis` 数据分析接口（入参：指标类型、时间范围、维度；出参：结构化结果 JSON）
- SpringBoot 侧提供 `AnalysisProxyService`，封装对 AI 服务的 HTTP 调用；生产时可由管理端看板触发，或以定时任务拉取。
- **本期交付**：`aimodule/` 目录骨架（FastAPI 入口、`langgraph` 工作流骨架、只读 DB 连接配置、`/health` 与 `/analysis` 占位实现、与后端对接的示例 DTO），不接真实大模型与复杂分析。

### 9.3 安全与数据
- AI 服务仅**只读**访问数据库，且只连接分析所需视图，不持有写权限。
- 鉴权双向：后端调用 AI 使用专用内部令牌，AI 接口不做公网暴露。
